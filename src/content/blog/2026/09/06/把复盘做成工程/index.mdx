# 把复盘做成工程：我的 AI 辅助开发工作流

前面几篇写了三个项目。这一篇想写的是另一个层面的东西——**这些项目是怎么被做出来、又被我自己搞明白的。**

起因很具体：我开始大量用 AI 写代码之后，发现瓶颈换位置了。以前的问题是"写得慢"，现在的问题是**"写得很快，但我看不懂自己仓库里发生了什么"**。面试里被追着问限流是固定窗口还是滑动窗口、恢复是从哪个阶段继续的时候，我答的是文档里的版本，而代码不是那样写的。

那不是记性问题，是**工作流问题**。所以后来我把两件事当成工程来做：文档体系，和复盘。

## 一、给每类信息指定唯一的主人

我最初的做法是"多记笔记"，结果是同一件事在四个地方有四个版本，改了一个忘了改其余三个。真正管用的是反过来：**每类信息只允许有一个主人，其它地方只能链接过去，不能复制。**

现在这套东西分了几个库，分工写在自己的 README 里：

```yaml
description: concepts=原理；method=怎么讲；题卡=巩固
```

具体是这样：

| 库 | 放什么 | 显式禁止 |
|---|---|---|
| `concepts/` | 原理正文（定义、机制、对比、易错点） | 不收面经、不刷卡、不写 STAR |
| `method/` | 怎么讲：简历、项目链路、答题话术、冲刺计划 | **不写纯概念长文** |
| `题卡/` | 间隔重复的挖空卡 | **不在题卡里扩写原理** |
| `handtear-engineering/` | 手撕代码的题目与正解 | 正解放最后，先自己写 |
| `面试 - 求职/` | 过程档案：场次、题面、复盘 | 不存学习材料 |

那张"谁写概念正文"的列是我专门加进去的，因为**它要回答的问题是"我现在想记这个，该记到哪"**——没有这一列，任何一条新信息都有四个可能的归宿，于是最后会出现在四个地方：

| 库 | 放什么 | 写概念正文？ | 显式禁止 |
|---|---|---|---|
| `concepts/` | 原理正文（定义、机制、对比、易错点） | ✅ 只这里 | 不收面经、不刷卡、不写 STAR |
| `method/` | 怎么讲：简历、项目链路、答题话术、冲刺计划 | ❌ | **不写纯概念长文** |
| `题卡/` | 间隔重复的挖空卡 | ❌ | **不在题卡里扩写原理** |
| `handtear-engineering/` | 手撕代码的题目与正解 | ❌ | 正解放最后，先自己写 |
| `面试 - 求职/` | 过程档案：场次、题面、复盘 | ❌ | 不存学习材料 |

配套的还有三条维护约定，写在 `concepts/README.md` 末尾：

```
1. 新概念只加/改进对应主题 md（不要再建子目录）
2. 题卡只挖空，不复制长原理
3. 面经弱项 → concepts 主题 或 考过索引
```

第一条是有来历的。我原来给 concepts 分子文件夹，很快就变成"这个知识点算网络还是算分布式"的纠结，同一个知识点被两边各写一遍。**扁平化之后"放哪"这个问题消失了**——主题只有十几个，一篇一个文件，加内容就是改文件。

第三条是我最满意的机制，它是个**双向回链**：面经里暴露的弱项链到 concepts 主题页，主题页文末的 `## 考过` 段落再链回具体场次。于是"我为什么写这段原理"和"这段原理在哪儿被考过"永远互相指得到。题卡的 README 里还有一条防漂移的约定：

> **原理主源**：concepts —— 不会的长文回主题页，**不要在题卡里扩写原理**。
> 每主题一个文件、一套 deck，口述与笔试知识合并维护，避免两套卡漂移。

"避免两套卡漂移"是踩过坑的总结：我原先口述题卡和笔试概念卡是两套，结果同一个问题出现了两个版本的答案，还都挺有道理。

**最后，这套体系必须自己记录自己的重构史。** 我在 `prep/README.md` 里留了一张「已收口」表，把旧目录名映射到新位置：

| 原目录 | 现在 |
|---|---|
| `online-core-interview-guide/` | → `method/` |
| `project-knowledge/` | → `method/projects/` |
| `八股题卡/` + `笔试概念题卡/` | → `题卡/` |
| concepts 分类子文件夹 | 已扁平删除 |

这张表的价值不在"记录历史"，而在于**三个月后的我在搜索框里打的会是旧名字**。没有这张表，我会以为那些内容丢了，然后重新写一遍。

## 二、复盘：把它当成一个数据结构的生成器

复盘最容易写成情绪日记。我的办法是**先定骨架，再填内容**——骨架固定了，写的时候就没有"这次要不要写点别的"的空间。

我现在的骨架大概是这个形状：

```
# 结论           —— 一段话说清这场怎么样
# 失分排序       —— 表格：优先级 | 问题 | 表现
# 一、亮点       —— 先写立住了什么
# 二、逐题……     —— 每道题的标准答
# 重来必改的五句话 —— 表格：场景 | 别说 | 改说
# 下一步行动     —— 表格：序 | 模块 | 动作 | 产出
# 三句话带走     —— 压缩成能记住的三条
```

三处设计我觉得是关键的。

**第一，「失分排序」用优先级列，不是按时间顺序列。** 面试过程是按时间走的，但如果按时间记，复盘读完你只知道"发生了什么"，不知道"先修哪个"。加上 P0–P3 之后，这份文档才变成待办清单。

**第二，「重来必改的五句话」用三列表格。** 这是我复盘里最有用的一个格式：

| 场景 | 别说 | 改说 |
|---|---|---|
| Redis 令牌桶 | 「Lua 具体不了解」 | 原子读 tokens + 补令牌 + 扣减；挂了 fail-open / closed + 本地兜底 |
| Claude API | 「没关注，借助 AI」 | 差异在 system / block / 流式 / tool_use；统一中间格式 + mapper |

**"别说"和"改说"并列，是逼自己给出替代方案。** 只写"下次要讲清楚"是没用的——什么叫清楚？写成具体的一句话，下次开口时才有东西可调。而且这一列天然会暴露另一个问题：如果我写不出"改说"，说明我不是表达不好，是**真的没搞懂**。这时候该回去补原理，而不是练话术。

**第三，「下一步行动」必须带产出列。** 不是"补 Go 并发"，而是：

| 序 | 模块 | 动作 | 产出 |
|---|---|---|---|
| 1 | Channel 边界四连 | 默写「buffered/unbuffered/关闭后收发/range 结束」各一句话 + 一个 demo 跑通 | 口头精确到不被追问 |
| 2 | 异或按位统计套路 | 重写 XOR 题，再用同套路刷 2–3 道 xor-pair 计数题 | 见到异或题先想「退化版 + 逐位奇偶」 |

**"产出"那一列是可验收的**。"口头精确到不被追问"和"见到某类题先想某个套路"都能拿下一次面试去检验。写不出产出的条目，通常是我还没想清楚要补到什么程度。

### 把失败压缩成可控量

这套格式真正要解决的问题是：**一场失败的面试，里面有多少是"我的问题"？**

我遇到过一场，最后卡在一个我认为与能力无关的点上，直觉是把结论停在"某个人/某个环节"上。我把整个过程完整写下来了，结论是这样的：

> **所以不要把这次写成一个"被人害了"的故事。** 它无法验证，也无法改进。能拿走的只有一条：**HR 面里关于时间的回答会被写进面评，而面评只有书写者能改**——这就是那个唯一值得改的杠杆。

配套的还有一段，是我给这件事定的收口方式：

> - **问题**：把结果全部归因到具体某个人身上，除了消耗，不产生下一次能用的东西。
> - **原因**：被卡在一个**与能力无关**的点上，愤怒与难过都完全正当——但情绪不是策略。
> - **改法**：允许自己难受，然后固定两句话收口……归因留余地，动作留在自己手里。

"归因留余地，动作留在自己手里"是我这套复盘法的核心。**不是说失败一定有我的责任，而是说复盘只能处理我有能力改动的部分。** 剩下的部分继续想下去，产出是零。

### 已知 / 未知分栏

还有一个格式我很推荐：**把"不知道的事"显式列出来，和"知道的事"并排。**

那场复盘里我做过一次：

| 已知（确认） | 未知（不猜） |
|---|---|
| mentor 面（单轮 gate）**通过** | 否决的**正式理由** |
| 面评写着「实习时间可能 3~4 个月」 | 「绝不仅仅因为你那句话」具体指什么 |
| 补救（补长期承诺）**无效** | 「上会看面评」这类传言的细节 |

右栏不是为了好看，是为了**拦住我自己在不可知的事情上反复消耗**。人很容易在无法验证的猜测上打转，尤其是失败的时候；把它明确归到"未知（不猜）"那一栏，等于给自己下了一道禁令。

同样的思路也用在技术复盘上。区分"我压根没学过这个"和"我学过但推不出来"，是两条完全不同的补课路径：

> 缺的是 **OS 并发原语**、**Go 并发模式**、**流式 Top-K 设计**、**图论建模技巧**——全部是固定套路，全部可 1~2 天内到默写级。

判断"这是固定套路题还是能力题"，比"这题我不会"有用得多。前者可补，后者只会让人泄气。

## 三、AI：它做什么，我审什么

我用的是 **Cursor 和 Codex**，模式基本是：**框架和结构由我定，Agent 在里面填充，我负责审。** 这个分工是有意的，因为"框架"是唯一不能外包的部分——目录怎么分、接口长什么样、状态放哪、失败怎么办，这些决定了系统能不能成立，而 Agent 在拿到模糊需求时给出的框架通常是"能跑但不可扩展"的那种。

### 我的五条审法

我把审 AI 产出的规矩写成了固定的五条，每次被问"你怎么保证质量"都照这个顺序讲：

1. **先让它拆需求、定结构，再填内容**——避免它一边想结构一边写实现，产出会自相矛盾；
2. **每次改动让它把 log 写到本地**——这样"发生了什么"有迹可查，而不是靠回忆 diff；
3. **单测必须有真值 / 夹具，不能靠 AI 自证**——这条最重要，下面单独说；
4. **用 repo 级的 Rules 约束输出**；
5. **关键逻辑转折点必须人工 review**。

**第三条是"AI 生成的测试"最大的陷阱。** 如果让 Agent 同时写实现和写测试，它写出来的测试测的是"它自己的理解"，两边一起错的话测试照样全绿。**测试的独立性来自真值来源，不来自写测试的人是谁。** 所以要么手写期望值，要么用夹具和快照把期望值固定在外部事实上。这一点我确实被问穿过——被追问"单测会不会跟着代码一起幻觉"时我答"出问题就 Review"，追问"没想过更严谨的方法吗"，我答"没想过"。

第四条也踩过坑。有个很典型的现象：**你让它别写某段内容，它会在前言里写一句"已去除某某问题"。** 你的指令本身被当成了内容输出。解法不是每次重新叮嘱，而是把规范落到仓库级的 Rules 文件里——**口头约束会漂，写进文件的约束才会稳定生效。**

### 一个具体做法：写需求书，而不是提问

这套工作流里我觉得最值钱的一个习惯，是**把"提问"改成"写需求书"**。

举个真实例子。我需要一套"拿到没见过的技术设计题怎么办"的方法论，我的做法不是去问 AI 几道题，而是写了一份带明确非目标的需求说明书：

```
# 需求：帮我建立「拿到没见过的技术设计题/思考题」的通用解题方法论

## 我的核心痛点（请围绕这个给方案）
1. **知识面窄**：OS/计网/组成原理普遍不会，且我清楚 4 天不可能补完整套知识
2. **最致命：没有「拿到一道没见过的题，脑子怎么转」的方法论**

## 我要什么（请不要给我以下东西）
- ❌ 不要八股背诵清单（TCP 三次握手过程、TIME_WAIT 时长这类）
- ❌ 不要押题（预测补面考什么）
- ❌ 不要只讲知识点（读写锁怎么写、Top-K 怎么解这类单点答案）
```

**那份"不要什么"的清单，是整个需求书里最重要的部分。** 因为 AI 的默认行为是给你一个覆盖面最广、最安全、最像教科书的答案——而教科书式的答案恰好是我说"不要"的那一类。不写清楚非目标，拿回来的就是对着一份目录背书。

这和写技术方案是同一种能力：**说清边界比说清目标更难，也更值钱。** 我在项目文档里做的是同一件事（"不是 LangChain 全托管；是可运行的执行层练习"），在需求书里做的还是同一件事。

### 还有两个用法

**让它做 mock 面试。** 我会在面试前一天让它扮演面试官，从简历逐句追问，记下卡壳的地方再模拟一次。这个用法的好处是**它不会因为礼貌而放过你**——真人朋友往往会手下留情。

**先想好解法再提示它。** 这是从我打竞赛的习惯迁移过来的：拿到题先自己在脑子里定一个方案，再看 AI 给什么，比对差异。直接让它先答，我会丧失"我本来会怎么想"这个参照系，也就失去了发现自己思路盲点的机会。复盘里把这条记成了那场面试"全场最有记忆点的回答"——说明它确实是我少数能讲得比别人具体的东西。

## 四、这套系统不解决什么

每次写方法论，我都想顺便把边界写清楚，因为**方法论最容易变成自我安慰**。

**第一，它不产生能力。** 文档体系只保证一件事：**能力被记录下来，漏洞被精确定位。** 定位完还得去补。我的复盘里出现过很多条"下一场要讲清楚"的话术，但真正让我答得上来的，是把 GMP、Channel 关闭语义、并发原语那些固定套路自己默写过一遍——不是把话术背熟。

**第二，我的项目里没有真实性能指标。** 这一点我要求自己写得非常死：简历模板里那些"支持 xxx QPS、P95 约 xxx ms"的位置，在我这里是**永远是 xxx**。项目文档里我也写明了"无生产 SLA / 真流量数据，别吹 QPS"。个人项目就是没有真实流量，**编一个数字比承认没有更糟糕**——因为它会被追问，而且一追就穿。

同理，前面那篇长视频 Agent 的文章里，我把 README 声称但代码里不存在的东西一条条列出来了。那也是这条原则的一部分：**如果我只能在"好看"和"可验证"之间选一个，我选可验证。**

**第三，这套系统是从被问穿之后才长出来的。** 它不是一开始就有的设计，而是每次答不上来、每次发现文档和代码不一致，就往里加一条规则。所以它的形状很像补丁——有用，但不好看，也肯定还有没补上的地方。

## 小结

如果只能留下三条：

1. **每类信息只能有一个主人。** 复制会产生漂移，漂移会让"我到底是怎么想的"变成一个无法回答的问题。
2. **把失败压缩成可控量。** 复盘的价值不在还原现场，而在产出一张带"产出"列的行动清单；剩下的部分明确归入"不猜"。
3. **AI 能写代码，但不能替你定框架，也不能替你校验自己。** 测试的真值必须来自外部事实，规范必须写进文件而不是靠每次叮嘱。

最后一句是我现在最相信的：**在 Agent 能写大部分代码的时代，稀缺的不是产出，是"能讲清每一行是怎么来的"。** 这套工作流存在的唯一理由，就是让我在别人（和几个月后的我自己）指着某一行问"为什么这样"的时候，答得上来。
