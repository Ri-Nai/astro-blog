# 手写 2D 平台跳跃：把瓷砖网格压成扫描线边表

大二小学期的时候，我和另外两个同学一起做了一个 2D 平台跳跃游戏：不用任何游戏引擎，纯 HTML5 Canvas + 原生 JavaScript 手写，带传送门机制、剧情和 Boss 战，关卡用一个 Python 写的编译器从表格编译出来。项目是 2024 年 8 月到 10 月做的，团队是 2 名开发 + 1 名美术。

现在回头看，这个项目值得写下来的不是"游戏做出来了"，而是里面几个具体的取舍：碰撞怎么保证不穿墙、扫描线合并到底省下了什么、以及**省下来的东西为什么不算复杂度降级**。最后一点是我后来复盘时最想写清楚的部分——当时我在简历上写了一句话，说服力其实不够。

## 为什么不用引擎

课程要求是一方面，更主要的动机是：**我想把物理和碰撞自己写一遍**。像素横版 2D 用 Canvas 2D 完全够，上 Unity 或者 Phaser 反而是把想学的东西藏起来了。

规模大概是：JS 4,360 行、HTML 764 行、CSS 1,185 行、Python 593 行，合计约 6,900 行，47 个 JS 文件。没有构建工具、没有依赖、没有网络请求，纯 `localStorage`。结构上分成 `Game`（主循环）、`View`（视图）、`Managers`、`Entities`、`Events`、`Tiles`、`utils`。

## 碰撞：先别让它穿墙

物理基类在 `Entities/Entity.js`，碰撞盒计算在 `utils/Hitbox.js`。这部分是我独立写的——项目文档里按提交历史统计过，这两个文件各自的改动全部来自我。

第一层是 **AABB + 轴分离**：x 和 y 分轴求解，返回值把结果压成 2 bit——`&1` 表示撞到 x 方向，`&2` 表示撞到 y 方向，调用方按键位处理静止、贴地和音效。

第二层是防隧穿，用的是**单位步长扫描移动 + 回滚**（`rigidMove`）：不直接把速度加到坐标上，而是按速度**逐 1 单位**步进，每步先试移动，一旦检测到碰撞就退回上一步并做速度修正（`-v × 0.95` 的反弹衰减）。

```js
// 思路示意：逐单位步进，撞了就回退并衰减
for (let step = 0; step < Math.abs(round(dx)); step++) {
  // 先挪 1 单位，再判定；命中则回退 + 速度修正
}
```

逐单位步进天然不会隧穿——因为单位步长下不存在"这一帧跨过了整堵墙"，代价是步数必须可控。所以速度上限被卡在 `MaxSpeed = 6` 单位/帧，两轴合计每帧最多 12 步。**先有速度上限，单位步进才成立**，这个先后关系是设计里比较关键的一点。

还有一个很小的细节：位移在步进之前先 `round()`。源码注释原文是——`//round是因为，如果沾上浮点数判断，这辈子有了`。说得粗糙，但意思是：浮点坐标会让"贴在墙上"变成一个坐标在墙体内外反复抖动的问题，`round()` 把它消掉。

## 真正的瓶颈不是隧穿，是候选集

上面那套做完之后不穿墙了，但每走一步都要"和什么比"？关卡是固定一屏的 **18 × 32 = 576 格**网格（40px/格，正好 1280×720）。如果直接拿整屏的实心地块去比，每帧的碰撞比较量是 12 步 × 231 格 ≈ 2,800 次。数字不大，可是它是在主循环里每帧都跑的。

关卡数据本来就是用 Python 从表格编译的，所以压这件事最自然的落点是**编译期**，分两层：

1. **按行游程合并（RLE）**：`fill_block()` 把连续相同的地块合成一条"条带"，产出 `blocks`；
2. **只保留暴露面**：`fill_edge()` 沿 x / y 各两个方向扫描，只保留该方向邻居为空的面，再按连续段合并。产出两份——`edges` 按材质切段（给渲染用），`super_edges` 不分材质（**运行时碰撞用这个**）。

这一步的依据很直接：**实心体内部的格子永远不可能被撞到**，因为要撞到它得先穿过它的边界。

这里有个我后来才理清的事实：**这两层压缩在项目早期就这样了，不是后期加上的优化。** 早期原型的编译脚本里就已经有 `fill_edge()`，但**运行时碰撞用的还是 RLE 之后的 `blocks`**（`let hitboxes = window.$game.map.blocks;`）。真正发生的变化是把运行时从"和块比"换成了"和边比"。所以我不打算把它讲成"先写了朴素版本再优化"——那不符合实际，而且这种故事听起来也比它本身更漂亮。

实测数据（全量 22 张可解析地图，40px/格）：

| 量 | 平均 | 最大 |
|---|---|---|
| 实心格（solid tiles） | 231 | 379 |
| `blocks` 条带（RLE 后） | 63 | 158 |
| `edges`（按材质切段） | 33.5 | — |
| **`super_edges`（运行时碰撞候选集）** | **24.9（中位 24）** | **48** |

于是每帧的碰撞比较量从 12 × 231 ≈ 2,800 次，降到 12 × 25 ≈ 300 次。候选集本身大概是实心格数量的 **1/9**，相对整屏 576 格约 **1/23**。

## 这里必须交底：这不是复杂度降级

上面那张表很容易被讲成"我把 O(n·m) 降到了 O(n+m)"。**这不是真的，我一开始也是这么写的，后来发现说不过去。**

段数取决于暴露面的**连续性**，而不是网格规模。大片连续的地面或者墙会合并成 1 段，所以实测值才这么低；但如果地形是**棋盘格**（每隔一格实心），每格的四个面全都暴露，而且彼此不相连，段数最坏就是 $\Theta(n \cdot m)$——四个方向各扫一遍，甚至会**高于**地块总数。

所以准确的表述应该是：

> 候选集从"实心地块数"降到"暴露面条带数"，收益来自关卡几何（大片实心 + 稀疏平台）与"只存边界、不存内部格子"，**不是复杂度类上的降级**。

"只存边界"这一半是**结构性**的收益——不管地形长什么样，内部格子都不会进候选集，这部分是稳的。"大片实心会合并成少数几段"这一半是**统计性**的收益，它依赖关卡长什么样，我拿不出对任意地形的保证。把这两半分开讲，比给一个大 O 记号诚实得多，也更经得起追问。

顺带一个容易忽略的设计：**渲染仍然按单位块绘制**。也就是说"渲染保真"和"碰撞省算力"是分开的——边表只用于碰撞查询，画面还是逐格画，所以合并不会让画面变糊。如果当时图省事拿 `super_edges` 去渲染，画面立刻就不对了。

## 手感：一个很小的状态机

跳跃手感的参数是实例化的：

```js
new Jumping(baseJump = 4, maxJump = 9, gravity = 0.5,
            coyoteTime = 8, jumpBufferTime = 15);
```

三件事：

- **可变高度蓄力跳**：按住空格时 `chargeTime` 累积，起跳初速在 `baseJump → maxJump` 之间插值，按得越久跳得越高。
- **土狼时间（8 帧）**：离开地面之后的 8 帧内仍然可以起跳。没这个的话，"刚走出平台边缘"这一下按跳会毫无反应，玩家会认为游戏坏了。
- **跳跃缓冲（15 帧）**：落地之前按下的跳跃会被暂存，落地瞬间自动起跳。这个是土狼时间的镜像——一个原谅"早了一点"，一个原谅"晚了一点"。

这两个数字是**调出来的**，而且我手里有证据：早期原型里的参数是 `new Jumping(5, 10, 0.5, 10, 1)`，最终版是 `(4, 9, 0.5, 8, 15)`——土狼时间从 10 帧收到 8 帧，跳跃缓冲从 1 帧放到 15 帧。**缓冲从 1 改到 15 这个跨度，说明我一开始完全低估了"提前按键"这件事有多常见。**

另外它们是**和帧率绑定**的：物理在更新前会先做 `deltaTime = 60 * deltaTime / 1000` 的归一化，所以这里的"帧"是"60fps 下的帧数"，`coyoteTimer` / `jumpBuffer` 递减的也是归一化后的值。按 60fps 折算，8 帧大约是 133 毫秒（这个换算是从帧率推的，原始参数只有帧数）。如果哪天要换固定步长，这两个数的量纲不受影响；但如果帧率基准变了，它们就得重调。

另外落在速度凝胶上会把土狼时间重置为 `1.3×` 并允许 `1.5×` 跳高——纯粹是给玩家的手感奖励，让"会用凝胶"这件事有正反馈。

## 传送门：旋转速度向量

门按 **4 个朝向** `facing` 建模，穿越时按这个角度旋转速度向量：

$$\theta = \frac{\pi}{2} \times \left((\text{inFacing} - \text{outFacing} + 4) \bmod 4\right)$$

旋转的结果是**模长不变、方向随门朝向转**，这就是 Portal 那套动量守恒的离散版本。还有一个兜底：出射速度如果太低会被补到 `1.2 × MaxSpeed`，保证实体一定能被"吐出去"，不会在两扇门之间原地卡住。

防卡墙的做法是：出口落点先做一次命中检测（`moveOutPortalPosition`），撞到边就返回 `null`、**放弃这次传送**。宁可传送失败，也不要把实体塞进墙体里——后者会产生一个"卡在墙里、每帧碰撞修正乱飞"的实体，比传送失败难查得多。

子弹也能穿门。这个不是顺手加的，它支撑了一整关的设计：Boss 的弹幕穿过门之后会变成玩家的子弹打回去。

## Python 关卡编译工具链

关卡不走硬编码。策划和美术直接改 Excel 表格（Sheet 名就是图层名），我用 Python 写了个编译器把它们编译成三份产物。编译端这个脚本在提交历史里的改动全部来自我：

- `maps/*.json` —— 碰撞边表与图层
- `events/*.json` —— 事件
- `viewdatas/*.json` —— 实体初始位置

编译过程里除了上面说的 RLE 和暴露面扫描，还用**并查集（DSU）**做连通块划分（事件区、剧情区、背景物件各跑一遍），用 **BFS** 在连通块里算出每个事件的上下游方向链（`predir` / `nxtdir`）——按钮、电线、门之间"谁触发谁"就是靠这个连起来的。剧情文本本身不在编译期生成，而是从已有的 `events/*.json` 读进来合并。

好处是关卡彻底数据驱动：改一张表、跑一次编译、游戏里立刻能看到。代价是多了一步编译，而且当编辑器不好用的时候，改关卡的体验会很差——当时没学 Tiled，现在会直接上 Tiled 或者一个 JSON 编辑器，把"表格"这一步省掉。

## 还有几个地方值得说

**帧率无关性有两套写法，语义不一样。** 物理用 `deltaFrame = 60 × dt / 1000`，把真实帧折算成"60fps 下的帧数"，速度量纲保持不变；而传送门子弹用 `target = SPEED × frameRatio`，是**按真实时间给步数**——掉帧时它一帧多走几步。两者不能混，混了就会出现"掉帧时子弹射程变短"这种怪事。

**暂停的时间补偿。** 暂停时主循环 `await wait(100)` 空转，恢复时把真实停顿的毫秒数加回时间戳（`loop(now + pauseTime)`）。不做这一步的话，恢复瞬间 `interval` 会暴涨，`deltaFrame` 跟着暴涨，物理直接"炸开"甚至穿透。这个补偿是必须的，不是优化。

**位运算风格统一。** 门索引取另一扇用 `i ^ 1`，返回值用 `1 << (i ^ 1)` 标记，入射朝向 `(facing + 2) & 3`，碰撞结果 2 bit 状态压缩。整个项目一致，读起来意外地顺。

## 已知的代价

这些我后来复盘时都写下来了，主动说完比被问住好：

- **边表没有空间划分。** 全图线性遍历，没有网格哈希或者四叉树。单屏 25 条边无所谓，但如果关是多屏、边表上百条，就该按屏幕/区块分桶。同时速度上限一旦提高，单位步进就不再安全，得换扫掠 AABB。
- **全局单例 `window.$game` 满天飞。** 没有依赖注入、没有模块化，所有东西挂全局。今天会拆成 ES Module + 构建工具。
- **魔数遍地。** 手感参数（0.5 / 0.3 / 0.1 / 衰减系数 / coyote 8 / buffer 15）散落在代码各处，没有集中配置。
- **`Entity.js` 里 `moveOutPortalPosition` 定义了两次**，内容相同。纯手误，没删掉。
- **数据加载是手写 JSONP。** `DataManager.loadJSON` 不用 `fetch`，而是 `document.createElement('script')` 把数据文件当脚本加载，Promise 的 `resolve` 被挂成回调，所以关卡 JSON 长这样：`window.$game.dataManager.resolve({...})`。动机是 `fetch` 在 `file://` 下被 CORS 拦死，而 `<script>` 不受限制——**双击 `index.html` 就能玩，不需要起本地服务器**。
  代价也说清楚：数据不再是严格 JSON（我实测 `Test.json` 因为一个尾逗号在严格解析下直接失败）、拿不到流式与超时控制。今天会直接上 `fetch` + 本地 dev server，或者干脆把数据打进 bundle。
- **暂停实现粗糙**：`while (isPaused) await wait(100)` 空转，是靠空轮询等状态翻转，而不是事件驱动。

## 小结

这个项目和后端岗没有直接关系，我不硬扯。它真正留下的东西是三样：**从零造轮子的完整经验**、**能对性能给出量化对比并知道自己论证边界在哪**，以及**愿意为一个手感参数调几十次的耐心**。

第二点是我现在最看重的。同一个项目，如果我只写"扫描线优化把复杂度从 O(n·m) 降到 O(n+m)"，那是一个会被一句话问穿的结论；写成"候选集从 231 降到 25，收益一半来自数据结构、一半来自关卡几何，最坏情况是 Θ(n·m)"，才是站得住的。
