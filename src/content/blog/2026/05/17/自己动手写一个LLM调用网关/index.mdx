# 自己动手写一个 LLM 调用网关

做视频理解 Agent 的时候，我发现一件很别扭的事：**调模型这一跳，和"任务怎么跑、状态怎么存"完全是两个问题，但代码里全缠在一起。**

于是我把调用层单独拆出来写了一遍——一个 OpenAI 兼容的 HTTP 网关，对外就是一个 `POST /v1/chat/completions`，内部负责屏蔽多家 provider 的差异、做 fallback、限流、token 计费。定位说清楚：**这是"可讲、可跑的最小实现"，不是完整商业网关。** 仓库里连密钥都能不填就跑起来，因为有 Mock provider。

拆分的边界我是写死在 README 里的：

> 与 DOVideo-AI **零重叠**：DOVideo 管「任务怎么跑、状态怎么存」（执行层）；本仓库管「调模型这一跳怎么稳、怎么记账」（调用层）。

甚至还有一句给未来的自己看的禁词表：

> 讲本项目时**不要**说 Checkpoint / 快照 / 任务调度——那是 DOVideo 的频道。这里只讲：适配器、fallback、限流、计费、trace。

事后看，这条约束比任何架构图都有用。它逼我在每个设计点上问一句：这属于"调用层"吗？不属于就别放进来。

## 骨架

Go 1.25，三个直接依赖：`gin`、`google/uuid`、`go-redis/v9`。没有 Prometheus client、没有配置库、没有日志库。四条路由：

```go
r.GET("/healthz", h.Health)
r.GET("/metrics", gin.WrapF(metrics.Handler()))
r.GET("/v1/billing", h.Billing)
r.POST("/v1/chat/completions", h.Completions)
```

`/healthz` 只回 `{"ok": true}`，**不探活 Redis、也不探活上游**——它是个进程存活探针，不是就绪探针。

## Adapter：差异只允许出现在这一层

统一接口就三个方法：

```go
// Provider 是适配器统一接口：新增 provider 只实现它，不动核心。
type Provider interface {
	Name() string
	Chat(ctx context.Context, req ChatRequest) (*ChatResponse, error)
	ChatStream(ctx context.Context, req ChatRequest) (<-chan Chunk, <-chan error)
}
```

注册进去的是四个实例：`mock-primary`、`mock-backup`、`openai`、`claude`——三个实现类型，Mock 注册了两次。真正有意思的是**差异到底有多大**：

| | OpenAI 兼容 | Claude |
|---|---|---|
| 鉴权头 | `Authorization: Bearer …` | `x-api-key` + `anthropic-version` |
| 正文 | `messages` | `messages` + 顶层 `system` |
| usage 字段 | `prompt_tokens` / `completion_tokens` | `input_tokens` / `output_tokens` |
| 响应正文 | `choices[0].message.content` | `content[]` 里挑 `type == "text"` 拼接 |
| 流式事件 | `data: {...}` + `[DONE]` | `content_block_delta` |

这些全在 Adapter 里被抹平成同一套 `ChatRequest` / `ChatResponse` / `Chunk`。核心代码调 `p.Chat(ctx, req)`，**它不知道对面是谁**。具体动作：**system 消息剥离**（Claude 把 system 放顶层字段，不在 `messages` 里；剩下的消息还要过角色白名单，不是 `user` / `assistant` 的一律降级成 `user`，否则上游直接 400）；**`max_tokens` 下限**（Claude 必填，所以 `max(req.MaxTokens, 1024)`）；**usage 换算**（`input_tokens` + `output_tokens` 才是统一的 `total_tokens`）；**模型名映射**（路由表里是逻辑名，以 `claude` 开头就原样透传）。

这里要交代一个**真实存在的妥协**：Claude 的流式是**伪流式**。代码注释是我自己写的：

> 流式 Claude 与 OpenAI SSE 事件格式不同；此处非流式再拆词 demo 透传语义。
> 生产应解析 `content_block_delta`；面试讲清「差异关在 Adapter」。

实现是先调一次非流式 `Chat`，再 `strings.Fields` 按空格切词吐出去——所以它**没有真正的首 token 延迟优势**，只是把"流式接口长什么样"演示完整了。还有一个纯粹的疏漏：`ChatRequest` 里有 `Temperature`，handler 也收，但**两个 Adapter 的请求体都没把它写进去**。字段被静默丢弃，这是 bug，不是设计。

## 先分类，再决定能不能切

fallback 最容易写错的地方是：把它写成一个 `for` 循环加 `if err != nil { continue }`。这样做的后果是——**用户参数写错了（400），你也会傻乎乎地把同一个错误请求再打给下一个 provider。**

所以我先把错误分成三档：

```go
const (
	ErrFatal ErrorClass = iota // 4xx / 参数错：不重试、不 fallback
	ErrRetryable               // 超时 / 5xx：可重试或 fallback
	ErrRateLimited             // 429：可排队或 fallback
)
```

判定函数只有一行：

```go
func (e *ProviderError) Retryable() bool {
	return e.Class == ErrRetryable || e.Class == ErrRateLimited
}
```

状态码到分类的映射是：429 → `ErrRateLimited`，`>= 500` → `ErrRetryable`，其它 → `ErrFatal`。网络层错误（含 `context.DeadlineExceeded`）统一进 `ErrRetryable`。

于是 fallback 的判定点就非常短：

```go
var pe *adapter.ProviderError
if errors.As(err, &pe) && !pe.Retryable() {
	return nil, err // 4xx：不 fallback
}
// 可重试 → 试下一个
```

**用 4xx 直接短路，省下的不是一次请求，而是一次注定失败的请求。** 链走完还没成功，才返回统一的 `all_providers_failed`。

链本身来自路由表——逻辑模型 → 主 provider + `Fallbacks` 切片，按顺序展开。这里有个取舍：**每个 provider 只尝试一次，没有重试次数上限常量，也没有退避**。全仓搜 `backoff`、`jitter` 都是零命中，切换就是立刻 `continue`。为什么不做退避？因为在这个语义里"下一个 provider"本身就是退避——换一家打，而不是打同一家。但真上生产的话，下游集体抖动时立刻切（而不是等一个随机退避窗口）会让雪崩传得更快。**这是我明确知道不够的地方。**

## 流式 fallback 的边界：首 chunk 之前

这是整个项目里我最想讲清楚的一段。

非流式请求失败了大不了重来一次，客户端什么都还没收到。**流式不行**——SSE 是一边生成一边往客户端写的，一旦已经吐出过字，再切换到另一个 provider，用户看到的就会是「前半句来自 A 模型、后半句来自 B 模型」的拼接产物。这种东西比直接报错更糟糕，因为它是**看起来正常但内容断裂**的失败。

所以规则定成：**流式只在"首 chunk 之前"允许切换。**

实现上有个细节我很满意——这里的"锁定"**不是一个布尔标志位，而是控制流本身**：

```go
select {
case <-ctx.Done():
	cancel()
	return nil, ctx.Err()
case err := <-errs:
	cancel()
	lastErr = err
	var pe *adapter.ProviderError
	if errors.As(err, &pe) && !pe.Retryable() {
		return nil, err
	}
	continue // 还没出字，可以换下一个
case c, ok := <-chunks:
	if !ok {
		cancel()
		lastErr = &adapter.ProviderError{Class: adapter.ErrRetryable, Code: "empty_stream", Message: "stream closed"}
		continue
	}
	// 首 chunk 已到：把已读 chunk 拼回，后续不再切模型
	// ...
	return &StreamSession{ ... }, nil
}
```

关键在最后那个分支：**它 `return` 了**。首 chunk 一到，函数直接返回 `StreamSession`，外面的 `for` 循环结束，此后再也没有机会进入下一轮 provider 尝试。为什么不用标志位？因为标志位要靠人记得检查，而这里"能不能切"和"代码还在不在循环里"是同一件事——**想做错都做不出来**。

首 chunk 还有个细节：它已经被从 channel 里读出来了，不能丢。所以要 `make` 一个新的 `out` channel，起一个 goroutine，**先把这个 chunk 补回去**再继续转发：

```go
out := make(chan adapter.Chunk)
errOut := make(chan error, 1)
go func(first adapter.Chunk) {
	defer close(out)
	defer close(errOut)
	defer cancel()
	out <- first
	// ... 继续转发剩余的 chunk
}(c)
```

这个 goroutine 里的错误只往 `errOut` 走，**不再触发链上切换**。语义很干脆：出了字之后，失败就是失败，只能断，不能补救。

代价也明确：**出字之后没有回滚、没有缓冲**。handler 收到 chunk 就立刻 `writeSSE` + `Flush`，全仓没有 buffer / rollback / discard 相关代码。要支持"已输出后还能切"，就得先在网关侧缓冲整段输出、等确认成功再吐给客户端——那样流的实时性就没了。**我当时的选择是保住实时性，代价是接受"出字后失败只断不重"。**

## 限流：三维令牌桶，用 scope 分桶

限流器接口收一个三维的键：

```go
// Dim 多维限流的维度键。
type Dim struct {
	User  string
	Model string
	Scope string // "chat" | "eval" —— 评测与日常隔离配额
}
```

`Allow` 依次检查三个桶，key 分别是 `user:<scope>:<user>`、`model:<scope>:<model>`、`global:<scope>`。三个维度是**与**的关系，任何一个拒绝就整体拒绝。

令牌桶本身是教科书实现：按 `elapsed × refillRate` 补令牌、封顶到 `burst`、不够一个就返回需要等多久。有两套后端：

- **内存版**：`map[string]*memBucket`，每个桶一把锁。默认走这条。
- **Redis + Lua 版**：只有设了 `REDIS_ADDR` 才启用。Lua 脚本把「读 tokens、补令牌、判断、扣减、写回」做成一次原子操作，避免多实例下的竞态；桶用 `HMSET` 存 `tokens` / `ts`，并 `PEXPIRE 60000`。

阈值全走环境变量，默认值是这样：

```
RATE_USER_RPS=20
RATE_MODEL_RPS=100
RATE_GLOBAL_RPS=500
RATE_BURST=50
```

Redis 那版有个明确的取向——**fail-open**：

```go
if err != nil {
	// Redis 故障时 fail-open，避免网关自己把业务打挂；面试可讲 fail-open vs fail-close
	continue
}
```

理由是：限流器是**保护手段**，不是业务功能。Redis 挂了就拒绝所有请求，等于网关亲手把业务打死；宁可短暂失去限流保护，也不要制造一次全站故障。反过来也有该 fail-close 的场景（计费、风控），所以这是个必须按业务选的开关，不是绝对正确的答案。

被限流时的响应：`429` + `Retry-After` 头 + 含 `error` / `scope` / `trace_id` / `retry_ms` 的 JSON 体。`Retry-After` 是 `int(wait.Seconds()) + 1`——**向上取整再加一秒**，避免客户端按精确值重试时因为时钟误差又撞一次。

### 三个粗糙点（我读自己代码时发现的）

**第一，scope 是"分桶"不是"分配额"。** `chat` 和 `eval` 会各自拿一套独立的桶，所以评测流量不会挤占日常流量的突发额度——这一半做到了。但两边**用的是同一组 `RATE_*` 阈值**，源码里没有任何 eval 专属的速率或 burst。所以准确的表述是「突发占用隔离」，**不是「配额上限隔离」**。我在笔记里曾经写成后者，是夸大了。

**第二，三维是顺序扣减，后面的维度拒绝时前面的不回滚。** `take` 已经 `b.tokens--` 了才轮到下一个维度判断，失败就直接 `return false`，被扣掉的令牌不会还回去。影响是：一个已经被全局桶拒绝的请求，仍然消耗了它自己的 user 桶和 model 桶额度。修法是先全部预检再统一扣减，但那样就得把三个桶锁在一起，复杂度和死锁风险都上来。

**第三，内存版桶永不淘汰。** `buckets` map 只增不减，没有 TTL、没有 eviction。用户 ID 如果是高基数（比如每台设备一个），长跑下去就是内存泄漏。Redis 版因为每个 key 都带 `PEXPIRE 60000` 反而不存在这个问题。

## context 取消传播

链路是这样的：`c.Request.Context()` 是根，注入 trace id，然后**每一跳都套一层自己的超时**：

```go
callCtx, cancel := context.WithTimeout(ctx, timeout)
```

超时优先级是：路由表里的 `Timeout` → 没配就用默认值（非流式 30s、流式 60s）。路由表里显式配的只有 5s（两个 mock 路由，用来测超时）和 60s（真 provider）。

上游请求用 `http.NewRequestWithContext` 构造，并且 `defer resp.Body.Close()`。这两句合起来保证了一件事：**客户端断开时，上游连接会被真正关掉，而不是留在那里继续生成 tokens。** 对一个按 token 计费的系统来说，这是省钱，也是防呆。

Adapter 内部的流式循环里也埋了取消检查：

```go
select {
case <-ctx.Done():
	errCh <- &ProviderError{Class: ErrRetryable, Code: "canceled", Message: "upstream canceled", Cause: ctx.Err()}
	return
case out <- Chunk{Delta: delta}:
}
```

**但这里有一个我必须说清楚的粗糙点。** `classifyNetErr` 把 `context.Canceled` 和 `context.DeadlineExceeded` 一起归到了 `ErrRetryable`：

```go
func classifyNetErr(err error) *ProviderError {
	if err == context.Canceled || err == context.DeadlineExceeded {
		return &ProviderError{Class: ErrRetryable, Code: "timeout", Message: err.Error(), Cause: err}
	}
	return &ProviderError{Class: ErrRetryable, Code: "network_error", Message: err.Error(), Cause: err}
}
```

而 `ChatStream` 首个事件前那个 `select` **同时**监听 `ctx.Done()` 和 `errs`。于是"用户在客户端按了取消"和"上游超时"这两件事在这一层**没有被区分开**：取消有可能被归类成可重试错误，走进 fallback 分支，去试下一个 provider。实际后果不严重——因为下一次尝试用的 `callCtx` 派生自同一个已经取消的 context，会立刻失败，最终还是返回错误——但语义是脏的，而且白跑了一次上游尝试。

正确的做法是把"调用方主动取消"单独拎出来，直接终止，不进 fallback。

顺带说明一句：我在笔记里写过这个设计"避免僵尸连接继续占配额"。**读回代码之后我要修正这个说法**——代码层面确实有 context 传递和 body 关闭，但没有针对僵尸连接的专门处理逻辑。那句话是我把设计意图当成了实现。

## 记账：按谁、按什么、按多少

计费的核心结构是这五个维度：

```go
type Labels struct {
	Tenant     string
	Experiment string
	Model      string
	Provider   string
	Scope      string // chat | eval
}
```

聚合的 key 是 `Tenant|Experiment|Model|Scope`——**注意这里没有 Provider**。这是想清楚"为什么记账"才定下来的：目的不是"看 provider 花了多少钱"，而是**"评测跑飞时一眼看出钱花在哪个实验上"**。所以 `Experiment` 必须有，`Provider` 只在单条 `Record` 里留作追溯，不进聚合维度。要看按 provider 的成本，得再加一个聚合维度——目前做不到。

成本估算明确是占位公式：

```go
// 粗估单价，面试讲「真实按模型价目表配置」
a.EstCostUSD += float64(r.PromptTokens)*0.000001 + float64(r.CompletionTokens)*0.000002
```

**`EstCostUSD` 字段名里的 Est 就是提醒：这是估算，不是账单。**

token 用量来源分三种：OpenAI 兼容直接读上游 `usage`；Claude 用 `input_tokens` + `output_tokens` 换算；Mock **自己估**，`(len([]rune(s)) + 3) / 4`，约 4 字符/token。流式取最后一个带 `Usage` 的 chunk，**一个都没有就记 0——这是个明确的窟窿**，产出了 token 但账上没记，真实系统里会造成对不上账。

## 可观测：只有 6 条序列

`/metrics` 是**手写的 Prometheus 文本格式**，没引 `client_golang`：

> Metrics 轻量 Prometheus 文本暴露，不引入 client_golang（网络受限时也能编过）。

暴露出来的全部序列就这些：

```
gateway_requests_total
gateway_errors_total
gateway_fallbacks_total
gateway_rate_limited_total
gateway_latency_ms{quantile="0.5"}
gateway_latency_ms{quantile="0.99"}
```

延迟是维护一个长度上限 2000 的滑动窗口，取分位数时排序后按下标取——`idx = int((len-1) * p)`，**不是标准插值**，数据量小的时候 p99 会跳。

trace 是独立的透传链路：请求头 `X-Trace-Id` 进来，没有就生成 uuid，**回写响应头**，同时塞进 context，被 Adapter 取出来发到上游的 `X-Trace-Id`。这样一次调用在网关、上游、客户端三边对得上同一个 id。

**但要交代清楚：没有结构化请求日志。** 全项目只有三行 `log.Printf`，都是启动信息。所以 trace id 只是被透传了，**没有一串日志可以用它串起来**。`observe` 包里还定义了一个 `Span` 结构体，但全仓没有一处构造或使用它——一个没写完的意图。

## 两个我明确知道自己没做的

**入站没有鉴权。** `gin.Default()` 之后没有任何鉴权中间件，`X-Tenant-ID`、`X-Experiment-ID`、`X-Traffic-Scope`、`X-User-ID` 全是**直接读头、不做校验**，默认值分别是 `default` / 空 / `chat` / 同 tenant。

也就是说：谁能访问到这个端口，谁就能自称是任何 tenant，并且把 `X-Traffic-Scope` 设成 `eval` 去用评测的桶。在"本地可跑的最小实现"这个定位下可以接受，**但它离生产差一个 API key 校验和配额授权**。这是清单上的第一条。

**测试只覆盖了两个分支。** 整个仓库只有一个测试文件，两个测试：

- `TestFallbackOn5xx`：主 provider 注入 5xx，断言发生了 fallback 且最终落在 backup 上；
- `TestNoFallbackOn4xx`：主 provider 注入 4xx，断言拿到的是 `Retryable() == false` 的错误。

**流式的首 chunk 状态机、限流器的 Lua 脚本、billing 聚合、SSE 解析，全都一行测试都没有。** 而首 chunk 状态机恰好是逻辑最绕的那一段。故障注入是靠 Mock 的 model 名后缀做的（`-fail5xx` / `-fail4xx` / `-slow`），所以补测试其实很便宜——这是我下一步最该做的事。

## 小结

这个网关真正立住的设计只有一条：**把"变化"关进最小的边界里。** provider 的字段差异关进 Adapter，错误语义关进 `ErrorClass`，限流算法关进 `Limiter` 接口（内存 / Redis 两套可直接替换），路由策略关进路由表。核心流程里你能看到的只有 `Retryable()` 这一个判断——**它不需要知道对面是 OpenAI 还是 Claude，也不需要知道令牌桶是内存还是 Redis。**

而上面那些粗糙点——被丢弃的 `temperature`、不区分的取消语义、不淘汰的内存桶、没有鉴权的入站、只测了两个分支的测试——我也都留在文章里。理由很实际：**一个能跑起来的最小实现，价值和它的边界是一体的。** 只讲设计不讲缺口，读的人（包括几个月后的我自己）会以为它比实际更完整。
