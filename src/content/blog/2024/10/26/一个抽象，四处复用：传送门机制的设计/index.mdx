# 一个抽象，四处复用：传送门机制的设计

大二小学期，我和另外两个同学一起做了一个 2D 平台跳跃游戏：不用引擎，纯 HTML5 Canvas + 原生 JavaScript 手写，47 个 JS 文件，没有依赖、没有构建工具、没有网络请求。项目做的是 2024 年 8 月到 10 月，团队是 2 名开发 + 1 名美术。物理与碰撞基类 `Entities/Entity.js` 是我负责的部分，传送判定就写在里面。

这一篇想讲的只有一件事：**「穿越传送门」这件事，是怎么被收敛成基类上唯一一个方法的，以及这个收敛换来了什么。** 碰撞怎么防穿墙、关卡怎么从表格编译出来，都是别的话题，这里不展开。

## 最自然的写法，和它为什么不行

如果不去想抽象，最直接的写法是：在 `Player.update` 里写一遍"碰到门了吗 → 算出出口位置 → 改坐标 → 转速度"，然后在 `Cube.update` 里再写一遍，`Bullet.update` 里再写一遍。

这种写法的问题不在于重复，而在于**每一份副本都必须重新想一遍边界情况**：出口落点撞到墙怎么办？出门速度要是接近零会不会卡在两扇门之间？刚被吐出来会不会立刻又被吸回去？这些问题的答案在四种实体上其实是同一个，但复制粘贴之后，它们变成了四份互不相关的假设。改对了一份，另外三份还是错的。

更隐蔽的问题是放置位置。如果只在"主移动循环"里判定传送，那么有些位移就绕过去了——比如原地站着不动的时候。

## 一根管道：让所有位移试探都经过它

`checkPortal(delta)` 在整个项目里只有两个调用点，但它们的位置比数量重要。

第一个在 `rigidMove` 的逐单位步进里——每走 1 个单位之前先试一次传送：

```js
let moveDirection = (delta, value) => {
    if (this.checkPortal(delta)) {
        return false;
    }
    this.hitbox.position.addEqual(delta);
    // ...
};
```

第二个在 `isOnGround()` 里——**判断脚下有没有地面之前，先试着往下挪 1 个单位**，而这一步也会触发传送：

```js
isOnGround() {
    if (this.velocity.y < 0)
        return false;
    if (this.checkPortal(new Vector(0, 1)))
        return false;
    // ...
}
```

也就是说，"走进传送门"在这个项目里不是移动系统里的一个特例分支，而是**顺路发生的**：任何一次试探性位移都会先经过它。把方法放在这个咽喉位置，后面所有实体都是白拿的——它们不需要知道传送门存在，只要它们会动。

## 一个方法，五件事

`checkPortal` 不长，但它一个人把穿越链条上的五件事全包了。

**入口检测。** 先检查两扇门是否都放下了（`type == -1` 表示那一侧还没开门，直接返回），再调 `portals[i].isMoveIn(this.hitbox)`。`isMoveIn` 的判定是两层的：实体碰撞箱必须在门的**平行轴上完整落入门宽**（`facing & 1` 决定查 x 还是查 y），再叠加一次普通的 AABB 相交。第一层是必须的，否则贴着门边缘的实体也会被判定成穿门。

**出口落点。** `moveOutPortalPosition(portals[i ^ 1])` 负责算，`i ^ 1` 就是"另一扇门"。

**防卡墙。** 上面这个方法命中墙体时返回 `null`，`checkPortal` 收到 `null` 就 `break`，**放弃这次传送**：

```js
let newPosition = this.moveOutPortalPosition(portals[i ^ 1]);
if (newPosition == null)
    break;
```

宁可这一次没传送成功，也不要把实体塞进墙体里。卡在墙里的实体会在后续每一帧被碰撞修正反复推挤，产生一个到处乱飞、极难复现的 bug；而"传送失败"只是一个可以接受的、稳定的结果。

**速度旋转。** `rotateVelocity(infacing, portals[i ^ 1].facing)` 按两扇门的朝向差旋转速度向量：

```js
rotateVelocity(infacing, outfacing) {
    let angle = Math.PI / 2 * ((infacing - outfacing + 4) % 4);
    this.velocity = this.velocity.rotate(angle);
    this.jumping.jumpVelocity = -this.velocity.y;
}
```

角度是 `π/2 × ((in - out + 4) mod 4)`，**模长不变、方向随门朝向旋转**——这就是《传送门》那套动量守恒在四个离散朝向下的版本。注意第二行：旋转完还要把速度的 y 分量反推回跳跃系统。不做这一步，"从天花板上的门掉出来"时跳跃状态还停在进门前的方向，实体一落地就会朝错的方向弹。

**最低出射速度保底。** 如果入射速度在门法向上的分量太小，会被补到 `MaxSpeed × 1.2`（`MaxSpeed = 6`，也就是 7.2）：

```js
if (this.velocity.dot(Portal.unitDirection[infacing]) <= this.MaxSpeed * 1.2) {
    if (Portal.unitDirection[infacing].x != 0)
        this.velocity.x = Portal.unitDirection[infacing].x * this.MaxSpeed * 1.2;
    else
        this.velocity.y = Portal.unitDirection[infacing].y * this.MaxSpeed * 1.2;
}
```

没有这个兜底，玩家慢慢"挤"进门就会以接近零的速度出现在出口，然后卡在门缝里。

最后还有一件事：传送成功后把 `this.inPortal` 置成一个几帧的缓冲值。从赋值时机看它像是为了防止二次进入，而能在代码里直接核实的效果是——**这几帧内水平输入不生效**（`updateXY` 会跳过 `updateX`，速度保持在刚旋转出来的那一份）。不管初衷是哪个，它都属于"出门口那几帧"的收尾，而这段收尾只有一处。

## 四种实体，一份逻辑

写完之后，调用方是这样的：

| 实体 | 怎么走到 `checkPortal` |
|---|---|
| `Player` | 继承 `Entity.update` → `updateXY` → `rigidMove` |
| `Cube` | 未被拾起时同样走 `updateXY` |
| `Bullet` | 自己写步进循环，逐步调 `this.checkPortal(direction)` |
| `Gel` | 同上 |

子弹和凝胶自己写循环，是因为它们的移动语义和玩家不一样（子弹用归一化方向逐格推进，凝胶要处理落地附着）。但**它们调的是同一个方法、同一份穿越规则**。四种实体，零份重复的穿越逻辑。

## 唯一的变体分支

整个传送链条上，实体之间的差异只有一个布尔判断：

```js
if (!this.isBullet)
    this.velocity = Portal.unitDirection[infacing].scale(this.velocity.magnitude());
```

它的意思是：对玩家和箱子，出门速度会被**吸附到门的法向**上、只保留模长；对子弹和凝胶，速度方向原样保留。

这里必须交个底：这个开关变量叫 `isBullet`，但把它置为 `true` 的有两个类——`Bullet` 和 `Gel`。它真正的语义是"保留自身弹道、不吸附到门的法向"，名字比语义窄了一圈。读代码的时候会先被这个名字骗一下。

## 这一处分支换来了什么

子弹的 `update` 里有这么一段：

```js
let flag = this.checkPortal(direction)
if (flag) {
    direction = this.velocity.normalize();
    this.type = flag >> 1;
    continue;
}
```

子弹的 `type` 初始是 `-1`，意思是"Boss 的子弹，命中扣玩家血"。穿过门之后，`type` 被重写成 `flag >> 1`，也就是出口那扇门的编号（0 或 1）。而命中判定那边只有两行：

```js
if (this.type != -1 && GLaDOS.hitbox.contains(centeredPosition)) {
    --GLaDOS.blood;
    this.destroy();
    return;
}
else if (this.type == -1 && player.hitbox.contains(centeredPosition)) {
    player.blood -= 1;
    this.destroy();
    return;
}
```

于是：**Boss 打出来的弹幕，穿过传送门之后变成了能伤害 Boss 自己的子弹。**

这件事不是为它单独写的功能。Boss 一共有四种弹幕形态——追踪弹、环形、矩形、花形——每一轮随机切一种，而这四种形态的代码里**没有一个字**提到传送门，它们只管按自己的几何形状生成子弹。子弹也只知道"每走一步先问一下 `checkPortal`"。

玩家能靠开门把弹幕反弹回去，是**四套弹幕生成器 + 一个 `type` 字段 + 那一处 `if (!this.isBullet)` 分支**共同的结果，没有任何一处是为它单独设计的。它是从统一接口里长出来的。

这大概是我在这个项目里最重要的一条经验：**抽象省下来的不是代码行数，而是让玩法的组合方式从"乘法"变成"加法"。** 反过来想一下：如果当初子弹为了"保持弹道"在 `Bullet.js` 里手写了一份自己的穿越逻辑（毕竟它确实和玩家不一样，这么做甚至显得很有道理），那它就和玩家那份分了家。后来想加"反弹弹幕"，就得在那份私有逻辑里改，而且只改到子弹那一份——Boss 战这关根本不会存在，我甚至不会想到它可以存在。

## 一致的风格也是一种抽象

还有一批东西严格说不算抽象，但作用类似：`i ^ 1` 取另一扇门，返回值 `1 << (i ^ 1)` 标记从哪扇门出来，`(facing + 2) & 3` 算门的入射朝向，碰撞结果压成 2 bit（`&1` 撞 x、`&2` 撞 y），`inPortal` / `isflying` 都写成同一个 `Math.max(x - deltaTime, 0)` 的倒计时。

单看每一处都是小事，但它们让"读完 `Entity.js` 就大概能猜出 `Portal.js` 会怎么写"变成现实。在一个 47 个 JS 文件、没有类型系统、没有 lint 的项目里，**风格一致差不多是唯一的静态检查**。

## 抽象之外的三件配套

传送门抽象解决的是"谁能穿门、穿过去之后怎么出来"。它之外还有三处设计，各占一段带过：

**关卡是编译出来的。** 关卡从 Excel 表格经 Python 工具链编译成三份 JSON（`maps` / `events` / `viewdatas`），运行时的碰撞只跟"暴露面条带" `super_edges` 求交——单屏实心格平均 231 个，合并成暴露面之后候选集平均约 25 条、最多 48 条。门能不能开也由数据决定：`Portal.valid` 的第一条检查就是 `edge.type != 2` 直接返回 `false`，也就是说只有编译期标记成"可开门"的面才允许贴门，顺带还要检查这条边够不够长（门口比边还宽就放不下）、以及会不会和另一扇门重叠。

**事件是边沿触发的。** 事件之间靠 `affect[]` 组成一张上下游信号图，但 `activate()` 里先看 `this.activated`，只有 `false → true` 那一次跳变才调 `onActivate()`。如果写成电平触发，玩家站在按钮上就会每帧重新触发一次下游，剧情会被反复播放。

**凝胶是 1D 区间集合的运算。** 新凝胶落到边上时，同类型重叠就 merge（并集），不同类型重叠就把旧的那条切开（差集）。所以白色凝胶可以覆盖蓝色凝胶的任意一段，而不是非得整条边换掉。

## 哪些地方抽象没兜住

主动说完比被问住好，这个项目的抽象只做对了一半：

- **`Entity.js` 里 `moveOutPortalPosition` 定义了两遍**，内容完全相同。逻辑收敛成了一个方法，代码里却留着两个同名方法。JS 类里后定义覆盖前定义，所以它"能跑"——它只是因为跑得通才活下来的。
- **`this.isBullet` 这个名字兜不住语义**（见上）。这是抽象边界开始渗漏的信号，我当时没管它，因为不影响运行。
- **边表和凝胶表都是线性遍历**，没有空间划分。单屏约 25 条边无所谓，关卡一旦做成多屏、边表上百条，就该按区块分桶。
- **万物挂在全局单例 `window.$game` 上。** 没有依赖注入也没有模块化，`checkPortal` 里要伸手去拿 `window.$game.view.portals`。所以这个"统一抽象"其实依赖一个全局单例才能工作——它不是纯函数，也没法单独测。
- **手感参数散落在代码各处**（土狼时间 8、跳跃缓冲 15、几档摩擦 0.5 / 0.3 / 0.1），没有集中配置，调参数靠全局搜索。
- **整个项目没有任何测试**：没有 `package.json`，没有一处断言。传送这套逻辑如果要改，唯一的验证方式是打开游戏自己玩一遍——而这恰好是最容易被说服自己"应该没问题"的验证方式。

## 抽象什么时候值得

我到现在也没有一个干净的标准，但有一条判据在这个项目上验证过：**抽完之后，有没有哪个功能是"不用改这段代码就能做出来"的。**

反弹弹幕算一个。Boss 的四种弹幕、子弹的激活逻辑、门的开合，全都没为它改动过一行，它是既有接口的自然组合。

反过来说，如果抽完之后每加一个新玩法还是得回到抽象内部改一行，那这个抽象就只是一堆被折叠起来的重复代码——折叠本身不产生价值，只是把成本挪到了下一次修改的时候。

更该担心的是抽早了。`checkPortal` 敢收得这么干净，是因为"穿越"对四种实体的语义**几乎完全一样**，差异只有一处，而且那一处恰好能用布尔开关表达。这是运气，也是这个具体玩法的性质。假如子弹的穿越和玩家有一半逻辑不同，那个 `if (!this.isBullet)` 就会长成 `if / else if / else` 的沼泽——那时候不是抽象坏了，而是**抽象选错了**：正确做法是把差异提成策略，或者干脆承认它们是两件事，别硬塞进同一个方法里。

边界不清楚的时候，多写一遍通常比抽错一次便宜。
